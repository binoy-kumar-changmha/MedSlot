## Part 2: Reflection Essay (500–700 Words)

<!-- ESSAY_START -->
While building MedSlot—a clinic appointment and billing manager spanning authentication, patient records, doctor availability, slot scheduling, and invoice settlement—I realized that backend endpoints multiply quickly once design patterns and validation errors are introduced. During CSE 3206 sessional labs, we practiced Git branching, design patterns, unit testing with mocks, Selenium browser testing, and continuous integration, yet our REST API endpoints were documented only informally in README tables. Because a full-stack clinic system requires strict agreement between its Express backend and React frontend, I selected Swagger/OpenAPI 3.0 as my self-directed software engineering tool.

Before committing to OpenAPI 3.0, I evaluated Postman Collections as an alternative. Postman works well for saving ad-hoc HTTP requests locally, but its collection format is tied to a proprietary client and often drifts out of sync with server code when developers forget to re-export JSON files. By contrast, OpenAPI 3.0 is a vendor-neutral declarative specification written in human-readable YAML right inside the repository. Using `swagger-ui-express` and the `yaml` parser, MedSlot serves an interactive Swagger UI at `/api-docs` and raw specification JSON at `/api-docs.json` directly from the running Express server. Any teammate, frontend component, or instructor can inspect schemas, authorize with a Bearer token, and execute live test requests without installing external desktop software.

Applying OpenAPI 3.0 to a real application surfaced three practical technical challenges that tutorials rarely mention. First, authenticating protected clinic routes required modeling `bearerAuth` under `components.securitySchemes` and attaching `security` blocks selectively so `/api/auth/login` and `/api/auth/register` remained public while patient, doctor, appointment, and billing routes enforced JWT-style HMAC tokens. Second, Express 5 uses `path-to-regexp` v8 and strict middleware ordering, so serving the built React single-page application caused a routing edge case where catch-all static fallback middleware initially risked shadowing `/api-docs`. Checking `!req.path.startsWith('/api-docs')` before `sendFile` resolved the conflict cleanly. Third, keeping documentation synchronized with evolving code proved critical: when we enforced a 30% discount cap and `409` slot-collision responses in services, hand-written prose became stale immediately. Writing `tests/unit/openapi.test.js` and adding a Selenium check confirming `/api-docs/` renders `"MedSlot Clinic API"` turned documentation into an automated CI gate rather than passive text.

Evaluating my learning resources taught me to separate authoritative specifications from quick blog posts. The official OpenAPI 3.0.3 Specification and Swagger's "Authentication" guide were essential for understanding `$ref` schema reuse, query parameter serialization, and HTTP status semantics (`401` unauthorized versus `402` gateway decline and `409` conflict), though their reference-style prose can feel dense without concrete examples. Conversely, short video and blog tutorials helped bootstrap `swagger-ui-express` inside Express in minutes, yet several outdated tutorials mixed Swagger 2.0 `definitions` syntax with OpenAPI 3.0 `components`, causing silent rendering omissions until I cross-checked every schema block against the official specification and Swagger Editor validation rules.

Building and documenting MedSlot revealed clear next steps for my software engineering growth. Next, I plan to learn **runtime OpenAPI contract validation middleware (such as `express-openapi-validator`) combined with Docker containerization**. Right now, `openapi.test.js` verifies YAML structure and module coverage in CI, whereas runtime contract validation middleware would guarantee during execution that no Express handler ever accepts malformed input or returns an undocumented field. Pairing contract-enforced OpenAPI services with reproducible Docker Compose setups and database migrations will move my future projects from well-documented student prototypes to production-ready microservices.
